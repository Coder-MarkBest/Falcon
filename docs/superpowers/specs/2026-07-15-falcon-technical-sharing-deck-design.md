# Android IPC 全景与 Falcon 实践：技术分享设计

- 日期：2026-07-15
- 交付物：可编辑 PowerPoint（`.pptx`）
- 页数：26 页
- 时长：45 分钟（35–38 分钟讲述，7–10 分钟问答）
- 听众：Android 工程师、架构师与技术负责人组成的混合听众

## 1. 分享目标

这份演示需要让听众在一次分享中完成三件事：

1. 建立 Android 跨进程通信方式的完整地图，理解各方式的语义、成本和适用边界。
2. 掌握 IPC 性能的真实成本来源，知道如何设计公平的 benchmark，而不是只记住一组设备相关的数字。
3. 理解 Falcon 在 Binder 之上解决了哪些工程问题，以及这些能力如何通过 KSP、生成代理与分发器、类型化 Bundle、服务发现、安全治理和事件生命周期管理实现。

Falcon 的定位必须准确：它不是绕过 Binder 的新传输协议，也不宣称突破 Binder 的物理性能上限。它是面向多进程 Android/车载系统的编译期类型安全与运行时治理层。

## 2. 叙事方案

采用“问题驱动 + 架构拆解”方案。

叙事因果链为：业务为什么需要 IPC → Android 提供了哪些机制 → 每种机制的成本与边界 → 原生能力为何仍留下工程复杂度 → Falcon 如何用薄封装解决这些问题 → 实现证据、性能口径和适用边界。

不采用以跑分为主线的方案，因为仓库 benchmark 的数字需要在同一真机或模拟器上运行后才有意义；不采用纯框架设计推演方案，因为会削弱用户要求的 Android IPC 全景介绍。

## 3. 内容边界

### 必须覆盖

- Binder/Raw Binder/AIDL、Messenger、ContentProvider、Broadcast、Socket、SharedMemory。
- 语义、线程模型、数据路径、序列化、拷贝、延迟、吞吐、易用性和典型场景。
- Binder 事务大小约束与大 payload 风险。
- Benchmark 的预热、稳态、分位数、同设备横向对比和语义公平性。
- Falcon 的开发者 API、总体架构、KSP 生成物、请求响应链路、稳定 methodId、类型化 Bundle、事件/流/回调、发现与重连、安全、限流、超时、监控。
- Falcon 的适用边界和不适用场景。

### 明确不做

- 不虚构具体设备性能数字。
- 不把 Broadcast 的双广播往返与原生 RPC 描述为完全等价。
- 不把 ContentProvider 的 insert+query 两次操作描述为单次事务。
- 不重新引入已删除的 SharedMemory 混合传输、CircuitBreaker、OTA 协议协商或运行时反射路径。
- 不使用大段源码截图；只展示帮助理解生成链路的最小代码片段。

## 4. 逐页结构

1. **封面**：Android IPC 全景与 Falcon 实践；副标题强调“从 Binder 成本模型到编译期治理”。
2. **业务场景**：用车载多进程拓扑说明系统服务、座舱、导航、媒体和第三方应用之间的通信需求。
3. **一次 IPC 调用**：用端到端轨迹展示代理、序列化、内核、线程调度、反序列化与服务执行。
4. **Android IPC 全景**：按 RPC、消息、数据访问、事件、流式/跨平台、大数据共享六类建立地图。
5. **Binder 基础设施**：进程边界、Binder 驱动、线程池、对象引用和调用方身份。
6. **性能成本模型**：上下文切换、数据拷贝、编解码、队列与调度、业务执行五类成本。
7. **Raw Binder / AIDL**：类型安全、Stub/Proxy、低额外开销、接口维护和线程模型。
8. **Messenger**：Message/Handler 串行模型、使用简单与吞吐瓶颈。
9. **ContentProvider**：面向数据模型、系统集成强、Cursor/URI 与额外抽象成本。
10. **Broadcast**：一对多事件通知、AMS 路径、后台限制与非 RPC 语义。
11. **Socket**：跨平台、流式、协议自由，以及连接、鉴权、序列化和生命周期成本。
12. **SharedMemory**：减少大块数据复制的价值，以及同步、FD、生命周期和安全复杂度。
13. **横向选型矩阵**：按语义、性能、类型安全、拓扑、数据规模和复杂度比较六类方式。
14. **公平 benchmark**：展示主进程、远程进程和五种机制的真实测试拓扑。
15. **瓶颈与优化优先级**：先减少调用次数和 payload，再优化编码与线程；最后才考虑更复杂传输。
16. **为什么需要 Falcon**：原生 Binder 性能足够，但接口生成、发现、连接、安全和可观测性仍需工程化。
17. **开发者体验**：接口注解、`Falcon.init`、生成 registry、注册与获取服务的最小代码。
18. **总体架构**：annotations → KSP → generated Proxy/Dispatcher/Registry → core runtime → Binder。
19. **KSP 生成物**：分别解释 Proxy、Dispatcher 和 Registry 的职责与编译期失败策略。
20. **请求响应调用链**：从业务方法到 Bundle、IpcEnvelope、IIpcHost、MessageRouter、Dispatcher 再返回。
21. **methodId 与 Bundle**：FNV-1a 签名哈希、重载安全、`IpcReply` 参数排除和类型化编解码。
22. **Event / Stream / Callback**：订阅、远程回调、Flow 解码，以及首订阅启动、末订阅取消的引用计数。
23. **发现与重连**：RegistryProvider、ContentObserver、PeerManager、bindService、linkToDeath 和指数退避。
24. **治理能力**：可信签名白名单、UID/PID 身份、访问规则、滑动窗口限流、超时与默认关闭的监控。
25. **Falcon 对比与边界**：对比 Raw AIDL 和其他机制，并说明小 payload、稳态 Binder、同版本 schema 等前提。
26. **总结与 Q&A**：三条结论——先选对语义、再控制成本、最后用生成代码和治理降低复杂度。

## 6. 性能表达原则

仓库 benchmark 比较 AIDL、Messenger、ContentProvider、Falcon 和 Broadcast。Falcon 测量的是预绑定后的生成 Proxy → Bundle → Binder → IpcHostService → 生成 Dispatcher → 实现类的稳态调用路径，服务发现不计入单次调用延迟，与 AIDL 的稳态测量口径一致。

PPT 中使用以下三类性能表达：

1. **机制级趋势**：根据调用路径和线程模型解释相对成本来源。
2. **可验证方法**：展示 warmup、迭代、avg、p50、p95、p99 和按 payload 分组的测量方式。
3. **实测结果模板**：提供可替换表格，明确要求在同一设备、同一次运行中比较。

没有设备运行证据时，不写入具体毫秒数，不使用暗示精确倍数的柱状图。
